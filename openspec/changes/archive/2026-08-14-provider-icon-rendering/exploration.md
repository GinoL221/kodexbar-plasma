## Exploration: Provider Icon Rendering

### Current State
`contents/code/ProviderIcons.js` declares `knownProviders` (49 keys) and a `key(value)` lookup that returns the lowercase match or `""`. `contents/ui/ProviderRow.qml:43-46` (`defaultIconSource`) and `contents/ui/ProviderSelector.qml:230` resolve each provider icon via `Qt.resolvedUrl("../icons/providers/" + key + ".svg")`, fed into `Kirigami.Icon { source: ... }` at `Kirigami.Units.iconSizes.smallMedium` (~22px). Provider icons are never set `isMask: true` — by design they are meant to render as full-color brand logomarks, not theme-recolored monochrome icons. Every `knownProviders` entry has a matching, case-correctly-named SVG file in `contents/icons/providers/`; the lookup/mapping layer is correct and out of scope.

All 49 SVGs were added in one bulk commit (`d027c1e chore: establish repository baseline`), apparently an unadapted import of an icon pack's "on-dark" variant.

**Verified defect inventory (spot-checked a sample of each category directly):**

1. **24 icons hardcoded pure white** (`fill="white"`, `fill="#FFFFFF"`, inline `style="fill:#fff"`, or `stroke="white"`) on a transparent canvas with no other color content: abacus, amp, antigravity, augment, azureopenai, bedrock, claude, codex, commandcode, copilot, crof, cursor, factory, gemini, grok, groq, jetbrains, kiro, ollama, openai, synthetic, warp, windsurf, zai. At ~22px these anti-alias into a solid white block — this is the root cause of the reported "white square" symptom. Confirmed by reading `claude.svg`, `openai.svg`, and `gemini.svg`: each is a single `<path fill="white">` carrying genuine, detailed brand-logomark geometry (OpenAI's mark has real interior negative-space sub-paths; Claude's is a real single-stroke asterisk glyph) — the artwork itself is correct and salvageable, only the fill color is wrong.
2. **2 duplicate-logo files**: `codex.svg` and `azureopenai.svg` are byte-identical to `openai.svg` (confirmed via `diff`, zero output). Both display the wrong brand mark entirely, not just the wrong color, and both additionally fall in category 1 (white fill).
3. **6 icons hardcoded near-black** (`#111111`, `#1a1a18`, `#34322D`, `#211E1E`) on a transparent canvas: alibaba, alibabatokenplan, kilo, manus, opencode, opencodego. Confirmed by reading `alibaba.svg` (`fill="#111111"`), `kilo.svg` (`fill="#1a1a18"`), `manus.svg` (multiple paths, all `fill="#34322D"`) — same defect class as category 1, inverted: near-invisible on Breeze Dark, same salvageable multi-path/single-path brand geometry.
4. **1 additional icon found during this verification pass, not previously enumerated**: `vertexai.svg` has `stroke="white"` on its outer hexagon outline and `fill="white"` on its inner hexagon fill (only a small `#4285F4` circle accent is colored). This is architecturally the same category-1 defect (hardcoded white) but was not part of the prior investigation's 24-icon list because the icon is not a *pure* single-white-shape — it has one non-white accent element. It renders as a mostly-white/blue blob at icon size and needs the same fix. **This exploration surfaces it as a required addition to the affected-icon list; sdd-propose should fold it into category 1's scope.**

**Confirmed correctly implemented** (use `fill="currentColor"`, unaffected, verified sample: `deepseek.svg`, `mistral.svg`, `perplexity.svg`) — these already follow the repo's intended pattern: a single `fill="currentColor"` (or `fill="currentColor" stroke="currentColor"`) attribute on the root `<svg>`, inherited by all child paths, with no hardcoded literal color anywhere in the file. This is empirical proof that `currentColor` resolves to something visible through this repo's actual `Kirigami.Icon` + Qt 6.11.1 rendering path today (14 provider icons ship this way and are not reported broken): deepgram, deepseek, devin, doubao, elevenlabs, kimik2, kimi, llmproxy, minimax, mistral, moonshot, perplexity, t3chat, venice, mimo.

**4 icons outside any prior category, checked in this pass and found fine, no action needed**: `codebuff.svg` (flat brand green `#44FF00`, correct as-is), `openrouter.svg` (already `fill="currentColor" stroke="currentColor"`, correct as-is — should probably be reclassified into the "correct" bucket, bringing it to 15), `stepfun.svg` (muted grays `#999999`/gradient, visible on both themes, not white/black, no action needed), and `vertexai.svg` (see category 4 above — action needed).

**QtSvg/Kirigami rendering constraint worth flagging for the design phase**: general Qt documentation and the Qt bug tracker state that Qt's raw `QSvgRenderer` does not resolve CSS `currentColor` against any painter/palette context — a widely reported QtSvg limitation across Qt5/Qt6. However, this repository's own 15 already-shipping `currentColor` provider icons are empirically rendering correctly through `Kirigami.Icon` (they are explicitly called out as "unaffected" and not part of the reported bug), which implies Kirigami's `Kirigami.Icon` / `KIconEngine` layer (used here even for raw `Qt.resolvedUrl()` file sources, not just icon-theme lookups) does resolve `currentColor` in this repo's actual Qt 6.11.1 + Plasma 6 environment, unlike bare `QSvgRenderer`. This is empirically settled for *monochrome* recoloring (single flat color per icon) but has not been separately verified for a genuinely multi-tone brand SVG (multiple distinct literal hex colors preserved side by side, e.g. a two-tone logo) — that combination does not exist yet among the 15 correct icons, all of which are single-tone. The design phase should do one manual `plasmawindowed` smoke check confirming light/dark theme recolor behavior before finalizing the exact fix pattern for every affected icon, rather than assuming the existing convention generalizes to every case.

### Affected Areas
- `contents/icons/providers/*.svg` — 24 pure-white icons (category 1) + 1 additional white/partial icon found this pass (`vertexai.svg`, category 4) + 2 duplicate-of-openai files needing distinct correct artwork (category 2) + 6 near-black icons (category 3). 33 files total need edits; 16 files (`openrouter.svg` plus the 15 already confirmed correct) need none.
- `contents/code/ProviderIcons.js` — read-only reference for this change; the `knownProviders` list and `key()` lookup are correct and must not change.
- `contents/ui/ProviderRow.qml:43-46`, `contents/ui/ProviderSelector.qml:230` — render call sites; confirmed they only need working SVG assets, not code changes, since `isMask` is intentionally unset and the URL-resolution logic is already correct.
- `tests/ProviderRowHarness.qml`, `tests/ProviderSelectorHarness.qml` — existing offscreen harnesses that exercise `defaultIconSource`/icon resolution; likely need new assertions covering theme-color visibility or at least non-broken SVG parsing for the corrected files, per `strict_tdd: true`.
- Nothing in `contents/config/`, provider selection logic, live refresh/reorder/removal, or the responsive layout from `single-product-transition-responsive-ui` needs to change — confirmed no code path in the render call sites depends on icon color.

### Approaches
1. **Recolor every affected icon to `fill="currentColor"` (adopt the existing 14/15-icon convention uniformly)** — strip every hardcoded white/black/near-black literal color from the 24+1 affected files and the 6 near-black files, replacing with `currentColor` at the root `<svg>` (matching `deepseek.svg`/`mistral.svg`/`perplexity.svg` exactly); for the 2 duplicate files, replace the borrowed OpenAI geometry with correct, distinct Codex/Azure-OpenAI brand path data authored the same way, using `currentColor`.
   - Pros: Matches the repo's own established, empirically-working convention exactly (15 icons already prove it works); theme-adaptive by construction (correct on both Breeze Light and Breeze Dark with zero extra logic); smallest conceptual diff — one attribute change per file for most cases; no QML/JS changes needed at all.
   - Cons: Loses any multi-tone brand color that might exist in a source logo (in practice none of the 30 affected files currently carry more than one literal color, so this is a theoretical cost, not an actual one for this change); relies on the not-fully-independently-verified assumption that Kirigami.Icon's `currentColor` resolution generalizes past the single-tone case already proven — mitigated by the one manual smoke check noted above.
   - Effort: Low–Medium (33 file edits, mechanical for the 31 already-correct-geometry files; the 2 duplicate files need real logo-geometry authoring/sourcing).

2. **Pick one fixed, theme-independent color per affected icon (e.g. a mid-gray or each brand's known accent hex) instead of `currentColor`** — hardcode a specific visible, non-white, non-black color per file.
   - Pros: Does not depend on `currentColor` resolving correctly through Kirigami.Icon at all, sidestepping the QtSvg `currentColor` limitation entirely; can preserve genuine multi-tone brand palettes (e.g. `codebuff.svg`'s flat green stays as-is, unaffected either way) if any icon actually needs more than one color.
   - Cons: Diverges from the repo's own established convention (would leave two different "correct" patterns coexisting: 15 files using `currentColor`, 33 using literal hex) with no stated reason; a single fixed color is not guaranteed to have adequate contrast against both Breeze Light and Breeze Dark panel backgrounds, reintroducing a milder version of the same visibility bug this change exists to fix; more design decisions (one color choice per brand) than approach 1.
   - Effort: Medium (same file count, plus a contrast-vetting pass per icon across both themes).

3. **Hybrid: `currentColor` for genuinely single-tone brand marks (the majority), literal-but-theme-safe color only for any icon whose authentic brand logo is inherently multi-tone** — apply approach 1 by default per file, falling back to approach 2 only for a file where the real brand mark cannot be represented in one color without misrepresenting the brand.
   - Pros: Keeps the dominant repo convention as the default; avoids forcing single-tone treatment onto a logo that is not actually single-tone, if such a case exists among the 33 affected files.
   - Cons: Requires a per-file judgment call during propose/design (does any of the 33 affected brand logos genuinely need >1 color to be recognizable?); on the evidence gathered here, none of the 24+1+6 affected files' current geometry uses more than one literal color already, so this decision may collapse to approach 1 in practice — the extra process may not be justified by real per-file variation.
   - Effort: Medium (same as 1, plus a documented per-file color-mode decision in the design doc).

### Recommendation
Approach 1 (uniform `currentColor` adoption) is the strongest default: it matches this repository's own established, already-shipping pattern exactly, requires no QML/JS changes, is theme-adaptive without extra logic, and every affected file's actual path geometry (as verified by direct inspection of `claude.svg`, `openai.svg`, `alibaba.svg`, `kilo.svg`, `manus.svg`, `vertexai.svg`) is already single-color-shaped — there is no real multi-tone content being lost. sdd-propose should confirm this with one smoke check (`plasmawindowed`, light and dark Breeze) on a converted sample before committing the full 33-file batch, per the QtSvg `currentColor` caveat noted above. The 2 duplicate-logo files (`codex.svg`, `azureopenai.svg`) need genuinely distinct path geometry, not just a color swap — this is the one part of the change that is authoring/sourcing work rather than a mechanical find-replace, and should be called out as its own task/reviewable unit.

### Risks
- `currentColor` resolution through Kirigami.Icon is empirically proven only for the already-shipping single-tone icons; it has not been independently verified in isolation from Kirigami's own recoloring behavior (as opposed to raw `QSvgRenderer`, which general Qt documentation says does not support `currentColor` at all). A pre-batch smoke check mitigates this; if it fails, approach 2 or 3 becomes the fallback.
- The 2 duplicate files (`codex.svg`, `azureopenai.svg`) require newly authored/derived path geometry, not a mechanical recolor — this is the highest-risk, most judgment-dependent slice of the change and the most likely place to introduce a wrong-logo regression if not reviewed carefully against the correct brand mark.
- `vertexai.svg` was not part of the prior investigation's enumerated lists; if sdd-propose scopes strictly to "the 24 + 2 duplicates + 6 near-black" it will miss this file. This exploration explicitly recommends folding it into category 1.
- Recoloring 30+ SVG files is a wide-surface but mechanically shallow change; under this project's `ask-on-risk` delivery strategy and 400-changed-line review budget, the batch may need splitting into reviewable slices (e.g. white-icon recolor / near-black recolor / duplicate-logo authoring as separate work units) rather than one commit.
- No CI QML runtime exists (per `openspec/config.yaml`), so visual correctness in both Breeze Light and Breeze Dark ultimately depends on the manual `plasmawindowed` smoke checklist, not an automated test; the offscreen harnesses can prove the SVG resolves/parses and the `source` URL is set, not that it is visually non-white.

### Ready for Proposal
Yes — propose a provider-icon-recoloring change scoped to `contents/icons/providers/*.svg` only (the 24 white + `vertexai.svg` + 6 near-black + 2 duplicate-logo files = 33 files). Do not change `ProviderIcons.js`, the render call sites' logic, package IDs, the `codexbar` CLI invocation, provider selection behavior, `contents/config/`, or the already-fixed responsive layout from `single-product-transition-responsive-ui` unless a smoke check proves a direct regression caused by this icon fix.
